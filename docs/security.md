# Security

This page lists the mechanisms for the phone-to-Mac connection and the status of each. The gateway listens on `127.0.0.1` ([ADR 0006](decisions/0006-gateway-binds-loopback-until-pairing.md)), so nothing on the LAN can reach it with the default settings.

## Threat model in one paragraph

The phone and the Mac share a local network that other people may also use, such as an office or a hotel. Recordings and transcripts can contain confidential customer information. An attacker on the same network must not be able to read jobs, submit jobs, or impersonate either device. The user's own devices are trusted once they are paired.

## Planned mechanisms

| Mechanism | Purpose | Status |
| --- | --- | --- |
| mDNS discovery | The phone finds the gateway on the LAN without the user typing an IP address. Discovery only finds the gateway. It grants no access. | implemented ([ADR 0011](decisions/0011-mac-inference-backend-and-mdns.md)) |
| Explicit pairing | The user starts pairing on the Mac (`fieldnote-gateway pair`) and enters the code on the phone. Nothing is trusted before that. | implemented ([ADR 0009](decisions/0009-pairing-and-sessions.md)) |
| Cryptographically random pairing tokens | A one-time code, shown on the Mac and entered on the phone, generated by a cryptographically secure random number generator. It is single-use and expires after 5 minutes. The code itself never crosses the network; the phone sends an HMAC proof. Repeated wrong proofs get 429. | implemented on the gateway |
| Short-lived session credentials | The phone trades its device secret for a 15-minute session token. Job requests carry only the session token. | implemented on the gateway |
| TLS with certificate pinning set at pairing | All traffic uses TLS 1.3 with a self-signed certificate. The pairing proof binds the code to the certificate fingerprint, and the phone pins that fingerprint afterwards. No certificate authority is involved. | implemented ([ADR 0010](decisions/0010-tls-and-pinned-pairing.md)) |
| Revocation | `fieldnote-gateway revoke <deviceId>` on the Mac. The gateway rejects the device's sessions and secret immediately. Unpairing on the phone deletes its stored credential; the Mac still lists the device until it is revoked there. | implemented |

## Already in place

- The gateway validates its environment at startup and exits if a value is invalid.
- The gateway accepts a caller's `x-request-id` only if it matches `^[A-Za-z0-9._-]{1,64}$`, so an attacker can't inject arbitrary text into the logs through that header.
- A transcript leaves the phone only to the paired Mac, over pinned TLS, and only when the user has left Mac use on.
- The gateway stores only SHA-256 hashes of pairing codes, device secrets and session tokens.
- A device can read only its own jobs. Another device's job ID answers 404.
